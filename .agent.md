## 1. Identidad del Proyecto

- **Nombre del Proyecto:** LocalCash
- **Breve descripción:** Sistema que permite a **usuarios de dispositivos Android** gestionar sus cuentas, registrar transacciones geolocalizadas en mapas e ingresar gastos compartidos, sin necesidad de **depender de servidores externos, contar con conexión a internet ni comprometer la privacidad de sus datos financieros**
- **Dueño del producto / Responsable:** Gustavo Gallegos
- **Repositorio:** https://github.com/GGallegosO/LocalCash

## 3. Comandos Principales

> Define aquí los comandos canónicos del ciclo de desarrollo. Cualquier agente debe usar
> EXCLUSIVAMENTE estos comandos; inventar comandos alternativos está prohibido (ver sección 7).

| Acción                | Comando                               | Cuándo usarlo                                         |
| --------------------- | ------------------------------------- | ----------------------------------------------------- |
| Levantar entorno dev  | `COMANDO_DEV = ./gradlew installDebug` | Compilar e instalar en el dispositivo/emulador para probar en caliente. **Requiere un dispositivo o emulador activo.** |
| Ejecutar tests        | `COMANDO_TEST = ./gradlew testDebugUnitTest`<br>`COMANDO_TEST_UI = ./gradlew connectedCheck` | Unitarios antes de cada commit; integración y UI antes de cada PR. `connectedCheck` **requiere dispositivo o emulador activo.** |
| Compilar / construir  | `COMANDO_BUILD = ./gradlew assembleDebug` | Antes de desplegar o validar empaquetado. Release: `./gradlew assembleRelease` / `bundleRelease`. |
| Linter / formateo     | `COMANDO_LINT = ./gradlew lint`       | Antes de cada commit (obligatorio, cero advertencias) |
| Instalar dependencias | `N/A` — el wrapper Gradle resuelve las dependencias automáticamente | Tras clonar o cambiar el manifiesto, basta con el comando de build. No existe un comando de instalación aparte. |

**Orden obligatorio antes de cerrar una feature** (Definition of Done de `tasks.md`):
`lint` → `testDebugUnitTest` → `connectedCheck` → `assembleDebug`. Se ejecuta `connectedCheck` al
final y no al principio: si falla, ya se perdió el ciclo de compilación.

> **Estado actual:** El proyecto Gradle ha sido inicializado exitosamente. La estructura `app/`,
> `gradle/` y los wrappers (`gradlew`) están presentes y los comandos canónicos son totalmente

## 5. Reglas y Convenciones

### 5.1 Arquitectura

- Patrón arquitectónico adoptado: **arquitectura por capas** (UI → dominio ← datos), con el
  dominio como núcleo sin dependencias de Android.
- Toda lógica de negocio debe residir en `app/src/main/java/com/localcash/domain/`; la capa `ui/`
  solo orquesta y traduce, nunca contiene reglas de negocio. `data/` implementa lo que `domain/`
  define y no decide reglas propias.
- Las dependencias apuntan hacia el dominio: `ui → domain ← data`.
- Ningún módulo puede importar desde una capa superior hacia una inferior sin justificación escrita en `plan.md`.
- Los cálculos financieros (reparto de deudas, saldos) viven en `domain/` y se prueban sin
  dispositivo; nada de lógica de dinero en `ui/` ni en un DAO.

### 5.2 Commits y ramas

- Formato de commit: Conventional Commits `tipo(alcance): resumen en imperativo` (ejemplo real del
  proyecto: `feat(autenticacion): agrega validación biométrica al acceso`).
- Tipos permitidos: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf`.
  - Divergencia conocida del historial: commits anteriores de documentación usan `dosc(sdd):`, tipo
    que **no está** en esta lista. No se replica: para documentación se usa `docs(agente)`.
- Un commit = una unidad lógica de cambio. Nada de "wip", "cambios", "update".
- Ramas: `main` protegida; trabajo en `<tipo>/<descripcion-en-kebab-case>` (ejemplo real:
  `docs/setup-sdd`).

### 5.3 Tipado y calidad

- Nivel de tipado exigido: **fuerte y estático** (Java; sin tipos dinámicos ni `Object` en la
  frontera del dominio).
- Cero advertencias del linter aceptadas en el código nuevo.
- Cobertura mínima de tests: **70%** en lógica de negocio y repositorios/DAOs.
- Nombres: descriptivos, en **inglés técnico** para identificadores de código, sin abreviaturas
  crípticas. La documentación y los comentarios de cara al usuario van en **español técnico**.

### 5.4 Manejo de errores

- Nunca silenciar un error: todo bloque de captura debe registrar con `Log` el contexto técnico
  (operación, id afectado) y/o propagar.
- Los errores de usuario se expresan con mensajes accionables; los técnicos se registran con
  contexto suficiente para depurar.
- Definir tipos/códigos de error canónicos en el módulo de dominio
  (`app/src/main/java/com/localcash/domain/error/`) y reutilizarlos; `ui/` los traduce a texto.
  - Código ya definido en la constitución del modelo: `CONTACTO_EN_USO`, que traduce el `RESTRICT`
    de las claves foráneas a un bloqueo explicable en la interfaz (ver `data-model.md` §4.2).

## 6. Qué NO Hacer (prohibiciones explícitas)

1. **NO exponer credenciales:** jamás escribir secretos, tokens, claves API ni contraseñas en el
   código, en la documentación o en el historial de Git. Usar variables de entorno vía `.env`
   (excluido de Git; documentar en `.env.example`).
2. **NO duplicar lógica:** si un comportamiento aparece dos veces, extraerlo a una unidad compartida.
3. **NO modificar fuera del scope:** un agente solo toca archivos requeridos por la feature activa.
   Cambios "aprovechados" van en otra tarea documentada.
4. **NO asumir tecnología no registrada:** prohibido usar cualquier librería, framework o servicio
   que no esté en `spec/constitution/tech-stack.md`. Ese archivo ya no tiene placeholders: el stack
   está cerrado, así que "aún no se ha decidido" no es una defensa válida.
5. **NO borrar ni reescribir la historia de Git** en ramas compartidas (`push --force` prohibido en `main`).
6. **NO agregar dependencias externas** sin registrarlas en `tech-stack.md` con su justificación.
7. **NO entregar código sin tests** para la lógica de negocio nueva.
8. **NO completar tareas sin actualizar la memoria** (ver sección 7).
9. **NO romper el pilar offline:** prohibido añadir librerías o funcionalidades que exijan backend,
   conexión permanente o API en la nube. La app debe funcionar íntegramente sin cobertura.
10. **NO representar dinero con `REAL` o `double`:** los montos y saldos van como `INTEGER` (tipo `long` en Java) en toda la capa de datos; `BigDecimal` solo en `domain/` (ver `data-model.md` §1.4).
    - **Adaptación local (CLP):** Los pesos chilenos se almacenan directamente en pesos (no centavos), ya que no hay subdivisión en circulación. Ejemplo: $1.000.000 CLP = `1000000L`.
11. **NO escribir migraciones destructivas:** prohibido `DROP TABLE` como estrategia de actualización
    y `fallbackToDestructiveMigration()`. La versión del esquema es `PRAGMA user_version`.

## 7. Registro de Memoria (obligatorio)

> Este proyecto funciona con memoria persistente en `/doc/`. Es la única fuente de verdad sobre
> lo que ya se decidió y ejecutó.

**Regla obligatoria:** tras finalizar CADA tarea, el agente DEBE crear el archivo
`doc/NNN-nombre-tarea.md` (numeración secuencial de tres dígitos, ver `doc/000-initial-setup.md`
como referencia de formato) conteniendo como mínimo:

- Fecha y nombre de la tarea ejecutada.
- Archivos creados y modificados.
- Decisiones tomadas con su justificación.
- Lecciones aprendidas (qué salió mal, qué se corregiría).
- Próximos pasos pendientes.

**Antes de iniciar cualquier tarea**, el agente DEBE leer `doc/` completo (al menos los últimos
registros) para no contradecir decisiones previas ni repetir trabajo.

Un registro incompleto equivale a una tarea no terminada.
